# AGENTS.md

> Contrato vivo deste projeto. Leia este arquivo primeiro em qualquer sessão nova, antes de fazer qualquer coisa. Mantenha-o enxuto — se uma seção crescer demais, mova o detalhe pra dentro de `docs/` e deixe aqui só um link.

## Sobre o projeto

Duas partes:
1. Galeria pessoal de gráficos em R, replicados a partir do [R Graph Gallery](https://r-graph-gallery.com/), adicionados aos poucos ao longo do tempo. Ver [README.md](README.md) para visão geral e estrutura de pastas.
2. Um site (`site/`, Astro) que exibe essa galeria de forma navegável e interativa. Contexto de produto/design completo em [PRODUCT.md](PRODUCT.md) — leia antes de mexer no site.

## Como rodar

Ambiente R já configurado (R + pacotes). Detalhes completos, caminhos e como instalar pacotes novos: [docs/SETUP.md](docs/SETUP.md). Não reinstale nada sem checar esse arquivo primeiro.

Site (`site/`): `cd site && npm run dev`.

## Adicionando um gráfico novo

Processo passo a passo: [docs/WORKFLOW.md](docs/WORKFLOW.md). Resumo: escolher gráfico não repetido → criar pasta em `graficos/<categoria>/<slug>/` a partir de `_template/` → copiar/rodar script → tentar versão interativa (prioridade, ver [PRODUCT.md](PRODUCT.md)) → preencher frontmatter+README da pasta **no padrão obrigatório** → registrar em [docs/PROGRESS.md](docs/PROGRESS.md).

O `README.md` de cada gráfico **é a página pública dele no site**, não anotação interna: frontmatter estendido (`resumo`/`pacotes`/`dados`/`nivel`/`tags`, que viram a ficha técnica) + 7 seções fixas, sem citar a fonte original em texto nenhum. Padrão completo no passo 6 do [WORKFLOW.md](docs/WORKFLOW.md).

## Git e commits

**Eu (a IA) nunca rodo `git add`/`git commit`/`git push` neste projeto — só o usuário commita**, pra manter o histórico de commits do repositório público (https://github.com/AugustoNeon/acervo-de-graficos.git) com autoria só dele. No fim de cada sessão onde algo mudou, eu forneço os comandos `git` prontos pra ele copiar e rodar, de forma simples e direta, sem executar nada sozinha.

## Primeira sessão — protocolo do agente

Ao abrir este repositório pela primeira vez numa sessão nova:

1. Leia este `AGENTS.md` inteiro.
2. Leia [docs/PROGRESS.md](docs/PROGRESS.md) pra saber o que já foi feito e não repetir gráfico.
3. Se for rodar ou instalar algo em R, leia [docs/SETUP.md](docs/SETUP.md) antes — não assuma caminhos padrão de instalação (ver "Lições aprendidas" abaixo).
4. Se for adicionar gráfico novo, siga [docs/WORKFLOW.md](docs/WORKFLOW.md) do início ao fim.
5. Cada informação mora em UM arquivo só — os outros linkam, não duplicam. Se notar algo desatualizado aqui ou em `docs/`, corrija na mesma sessão em que perceber, não deixe pra depois.

## Convenções

- Um gráfico = uma pasta (`script.R` + `output.png` + `README.md`), nunca vários gráficos no mesmo script.
- Não refatorar/"melhorar" o código do R Graph Gallery — o objetivo é replicar e entender, não redesenhar.
- Categorias de `graficos/` espelham a navegação do próprio site — crie uma categoria nova só se nenhuma existente encaixar.

## Lições aprendidas

_(mais recente no topo — poda entradas muito antigas/óbvias de tempos em tempos)_

- **2026-07-30**: capturas de `webshot2::webshot()` em fontes muito pequenas (o padrão do `collapsibleTree` é `fontSize = 10`) podem sair com uma franja de cor por letra no `output.png` — cada caractere de um rótulo aparecia com uma cor diferente (azul, rosa, verde...), mesmo o `<text>` correspondente no DOM tendo `fill: rgb(0,0,0)` puro (confirmado abrindo o mesmo `widget.html` num navegador de verdade — só o screenshot vinha errado, o widget real nunca mostrou isso). Causa provável: anti-aliasing por subpixel na suavização de fonte do Chromium headless em tamanho de fonte muito pequeno. Resolvido passando `zoom = 2` (ou mais) pro `webshot2::webshot()` — a super-amostragem elimina a franja sem mudar o enquadramento (mantém a mesma proporção de `vwidth`/`vheight`, só sai com o dobro de pixels). Detectado no [dendrograma-interativo](graficos/part-of-whole/dendrograma-interativo).
- **2026-07-30**: `collapsibleTree` (htmlwidget) tem o mesmo defeito de sizing já catalogado pra `ggiraph`/`streamgraph` — o wrapper `.collapsibleTree` nasce com `width:960px;height:500px` fixo (sizingPolicy `browser.fill:false` do `htmlwidgets`) e o `<svg>` interno só tem `width`/`height` em px, sem `viewBox`, então estoura a largura do iframe do site. Corrigido acrescentando `.collapsibleTree` à lista de seletores do fix genérico em [`[slug].astro`](site/src/pages/graficos/[category]/[slug].astro) (mesmo mecanismo: sintetiza um `viewBox` a partir do `width`/`height` do SVG, depois força `width:100%;height:auto` no wrapper e no SVG) — nenhuma mudança de código nova precisou ser escrita, só estender a lista já preparada pra isso.
- **2026-07-30**: gráficos de `ggiraph::girafe()` exportados via `saveWidget(..., selfcontained = FALSE)` podem nascer com o `sizingPolicy` de `htmlwidgets` marcado como `"browser":{"fill":false}` — quando isso acontece, o `htmlwidgets.js` **nunca** reescala o `<div class="girafe">` pro tamanho do container, e ele fica travado no `width_svg`/`height_svg` fixo em px (convertido pra px pelo default de 960×500 do próprio `htmlwidgets`, não pelas dimensões pedidas), estourando a largura do iframe do site — sintoma: gráfico cortado na lateral + barra de rolagem horizontal dentro do widget (foi assim que apareceu no [circle-packing-simples](graficos/part-of-whole/circle-packing-simples)). `opts_sizing(rescale = TRUE)` no `girafe()` **não resolve** isso — essa opção é sobre o rescale interno do SVG do ggiraph, não sobre a política de fill do htmlwidgets em volta dele. Um gráfico irmão (`linha-interativa-ggiraph-css`) nunca teve o problema só porque seu `widget.html` foi montado à mão (múltiplos painéis) sem a tag `<script type="application/htmlwidget-sizing">`, o que faz o `htmlwidgets.js` cair num caminho que reescala sozinho. Correção geral aplicada em [`[slug].astro`](site/src/pages/graficos/[category]/[slug].astro), no handler de `load` do iframe: força `width:100%;height:auto` em qualquer `.girafe` (e no `<svg>` dentro dele, que não tem `width`/`height` próprios, só `viewBox` — por isso reescala mantendo proporção) antes de medir a altura do conteúdo. Como o seletor é `.girafe` (não um genérico `.html-widget`), não afeta leaflet/plotly/dygraphs/networkD3, que já se redimensionam sozinhos. Vale essa checagem (`bodyScrollWidth` do iframe vs `clientWidth`) em qualquer gráfico novo de `ggiraph` antes de fechar.
- **2026-07-29**: **a versão interativa e o `output.png` de um mesmo gráfico precisam ser comparados lado a lado antes de fechar o gráfico** — não basta cada um estar "correto" isoladamente. O `output.png` é a miniatura do card na galeria, então o usuário vê a estática primeiro e a interativa depois: qualquer divergência de paleta lê como bug, e foi exatamente essa a reclamação em 3 gráficos de uma vez (hairball, rede direcionada, circle packing hierárquico). A causa raiz é sempre a mesma: **pacotes de widget não têm o sistema de escalas do `ggplot2`**, então o que no estático é uma linha (`scale_colour_distiller()`, `scale_edge_alpha()`) precisa ser calculado à mão e passado pronto no widget — e é fácil "esquecer" e deixar uma cor fixa no lugar de um gradiente. Duas regras práticas: (1) definir a paleta/rampa **uma vez** numa variável e alimentar as duas versões com ela, nunca repetir hexadecimais; (2) conferir de fato a imagem do widget, via `webshot2::webshot()` sobre o `widget.html` (ver [SETUP.md](docs/SETUP.md)) — ler cor no DOM/canvas engana, porque confirma que o widget respeita o próprio código sem revelar que o código diverge do estático. Equivalências já mapeadas: `scale_colour_distiller(palette=P)` ≡ `scales::gradient_n_pal(RColorBrewer::brewer.pal(7,P))(scales::rescale(x))`; opacidade por elemento no `visNetwork` (que só aceita um valor global) ≡ embutir o alpha na cor via `rgba()` numa coluna `color.color`.
- **2026-07-29**: `circlepackeR` (widget de circle packing hierárquico) **não consegue uma cor por nível da hierarquia** — só aceita `color_min`/`color_max` e interpola em HCL num domínio de profundidade **fixo em -1..5**. Como cada nível ocupa 1/6 desse domínio e o `d3.interpolateHcl` do d3 v3 percorre no máximo 180° de matiz no total, dois níveis vizinhos ficam limitados a ~30° de matiz de diferença (teal→dourado, ~98°, é impossível). Pior: o CSS do pacote pinta as folhas de branco (`.node--leaf { fill: white }`), ignorando o gradiente. Não há parâmetro que resolva — a saída usada foi sobrepor CSS (raiz + folhas) e um `<script>` que repinta os níveis do meio lendo `__data__.depth` de cada círculo, empacotados junto do widget via `htmltools::save_html()` + `tagList()` (mesmo padrão dos gráficos de `ggiraph`). Detalhe que ajuda: a função de zoom do pacote anima só posição/raio, nunca `fill`, então repintar uma vez basta. Ver [graficos/part-of-whole/circle-packing-hierarquico/script.R](graficos/part-of-whole/circle-packing-hierarquico/script.R).
- **2026-07-29**: ainda no `circlepackeR`, um segundo defeito, **intermitente e silencioso**: ele mede o container uma única vez no render (`diameter = Math.min(rect.width, rect.height)`) e o handler `resize` dele é uma **função vazia**. Se nesse instante o container ainda não tiver layout — acontece de vez em quando dentro de um `<iframe>`, tipicamente na primeira carga após reiniciar o dev server — o diâmetro sai `0`, o SVG nasce `0x0` e **fica vazio pra sempre**, sem erro no console. Pior: o widget também escreve `height: 0px` no `iframe` que o contém (`d3.select(self.frameElement)`), o que anula a altura de fallback do CSS do site e deixa a página com um buraco. Como o `renderValue` do pacote limpa o container antes de desenhar, refazer o desenho é idempotente e seguro: a correção usada re-invoca `renderValue` uma vez, via `HTMLWidgets.widgets` + a carga JSON da tag `script[data-for=...]`, quando o container já tem tamanho real. Sintoma a procurar quando um widget "desaparece" sem erro: `svg` com `width="0"` e o `iframe` com `height: 0px` inline.
- **2026-07-29**: ao testar JS injetado num widget, prefira `setInterval` a `requestAnimationFrame` pra esperar o widget renderizar — o pane de preview não compõe frames quando não está visível (ver entrada de 2026-07-23 abaixo), então um loop de `rAF` nunca avança ali, enquanto timers rodam normalmente.

- **2026-07-27**: o canvas WebGL gerado por `rgl::rglwidget()` nasce com **largura fixa em pixels**, herdada do tamanho do dispositivo criado em `open3d(windowRect = c(...))` — não é responsivo por padrão e estoura a largura do container (página do site, iframe) quando esse container é mais estreito que o tamanho original, gerando rolagem horizontal. Corrigido com uma regra CSS simples (`.rglWebGL canvas { max-width: 100%; height: auto !important; }`): o motor de renderização do widget detecta a mudança e recalcula a resolução interna do canvas sozinho, sem distorcer a cena. Ver [graficos/correlation/dispersao-3d-cafes/script.R](graficos/correlation/dispersao-3d-cafes/script.R).
- **2026-07-27**: `Rscript.exe -e '<script multi-linha entre aspas simples>'` chamado via Bash (Git Bash) neste Windows dá **segmentation fault** (exit code 139) quando o script usa certas combinações de aspas/quebras de linha — reproduzido consistentemente com `rgl` (`legend3d()`, chamadas encadeadas). Não é um bug do pacote R: o mesmo código rodando a partir de um arquivo `.R` de verdade (`Rscript.exe script.R`) funciona sem erro. Ao testar snippets rápidos de R via Bash, sempre escrever num arquivo `.R` (Write) e rodar `Rscript.exe caminho\script.R`, nunca `Rscript.exe -e '...'` com script grande/multi-linha inline.
- **2026-07-27**: `rgl::legend3d()` **não renderiza** quando a sessão roda com `options(rgl.useNULL = TRUE)` (necessário pra `Rscript` não-interativo sem janela gráfica real — ver [SETUP.md](docs/SETUP.md)) — a função não dá erro, só o overlay de legenda simplesmente não aparece no `snapshot3d()` final, sem nenhum aviso. É uma limitação conhecida do mecanismo de composição de overlay do `rgl` (`bgplot3d()`) em modo headless. Solução usada: gerar o `snapshot3d()` só com a cena 3D (sem legenda) num arquivo temporário, depois reabrir esse PNG com `png::readPNG()` + `rasterImage()` dentro de um device `png()` normal do R base e desenhar a legenda por cima com `legend()` comum — ver [graficos/correlation/dispersao-3d-cafes/script.R](graficos/correlation/dispersao-3d-cafes/script.R).
- **2026-07-24**: `Rscript.exe "graficos\<categoria>\<slug>\script.R"` (comando exatamente como documentado no passo 4 do [`WORKFLOW.md`](docs/WORKFLOW.md)) **não** muda o working directory do R pra pasta do script — ele herda o cwd de onde o terminal foi chamado (a raiz do repo, geralmente). Como `script.R` sempre salva com caminho relativo (`ggsave("output.png", ...)`), isso faz o PNG cair na **raiz do repo** em vez da pasta do gráfico, sem nenhum erro/aviso (o script roda normal, só o arquivo aparece no lugar errado). Sempre `Set-Location` pra dentro da pasta do gráfico antes de rodar o `Rscript`, e voltar pra raiz depois (`Set-Location <pasta>; & Rscript.exe script.R; Set-Location <raiz>`), ou conferir com `ls` que o `output.png` realmente apareceu dentro da pasta certa antes de seguir pro próximo passo.
- **2026-07-23**: em widgets D3 feitos à mão com `<svg viewBox="0 0 W H" width="100%">` (pra caber gráficos grandes/largos numa tela menor), qualquer texto **dentro** do SVG (`font-size` em unidades do usuário) reescala junto com esse `viewBox` — quanto maior `W`/`H` em relação ao tamanho real exibido, menor o texto fica na prática, podendo virar ilegível sem nenhum erro/aviso. Legenda e textos de instrução devem ficar em HTML normal fora do `<svg>` (`<div>` com CSS `font-size` de verdade), nunca como `<text>` dentro do SVG, quando o SVG tiver um `viewBox` que cresce com a quantidade de dados. Detectado no [arc diagram](graficos/network/arc-diagram-d3) depois que a rede cresceu e a legenda embutida no SVG ficou minúscula.
- **2026-07-23**: o pane de preview do Browser (usado pra testar widgets nesta sessão) parece não compor/renderizar frames quando não está em foco/visível (mesma causa provável do timeout de screenshot já registrado abaixo) — isso quebra qualquer teste de `d3.transition()`/`requestAnimationFrame`/CSS transition via JS: o código roda sem erro, mas o estado nunca avança mesmo esperando bastante tempo (testado com `d3.zoom` + `.transition().duration(400)`, o `__zoom` do nó nunca mudava). Eventos DOM síncronos (`wheel`, `mousedown`/`mousemove`/`mouseup`, `dblclick`) funcionam normalmente e são testáveis via `javascript_tool`. Ao adicionar interatividade que dependa de animação, prefira uma versão sem `.transition()` (muda o estado instantaneamente) quando precisar verificar via este ambiente — ou avise o usuário que a suavidade da animação fica sem confirmação automática.
- **2026-07-23**: quando um widget D3 feito à mão precisa de muitos dados (esse é o caso do arc diagram, que cresceu de 14 pra 72 nós), evite duplicar o array de nós/links entre `script.R` e o `<script>` do `widget.html` — depois de uma mudança fica fácil os dois dessincronizarem. Melhor: o R gera os dados uma vez e exporta via `jsonlite::toJSON()` pra um arquivo `widget_files/data.js` (`const nodes = [...]; const links = [...];`), que o `widget.html` carrega com uma tag `<script src="widget_files/data.js"></script>` comum — funciona em `file://` e via servidor igual, ao contrário de um `fetch()` de JSON (que quebra por CORS quando o arquivo é aberto direto sem servidor). Ver [graficos/network/arc-diagram-d3/script.R](graficos/network/arc-diagram-d3/script.R).

Sempre que adicionar um gráfico novo com o dev server já de pé, reinicie o servidor (`npx astro dev stop` + `npm run dev` de novo) depois de rodar o sync, antes de testar no navegador.

## Decisões fechadas

_(mais recente no topo, formato: decisão. Por quê. Custo.)_

- **2026-07-30**: a versão interativa (`widget.html`) precisa ser **visualmente equivalente** ao `output.png` — mesmos rótulos, mesma grade/anotações, mesmo layout geral, não só a mesma paleta de cor. Se a biblioteca interativa não conseguir reproduzir isso de forma fiel, a prioridade é **não publicar** a versão interativa (`interactive: false`, sem `widget.html`) em vez de publicar uma que parece outro gráfico. Por quê: pedido explícito do usuário, depois de notar que o [circular-barplot-empilhado](graficos/ranking/circular-barplot-empilhado) tinha um `output.png` com grade/rótulos/arco customizados, mas a versão interativa (`plotly::plot_ly(type="barpolar")`) saiu com o grid genérico do próprio plotly, sem nenhum dos rótulos ou arcos — o card da galeria (que usa o `output.png`) prometia uma coisa e a página do gráfico entregava outra. Generaliza a entrada de 2026-07-29 sobre divergência de *cor* entre estático/widget (ver "Lições aprendidas") pro caso mais amplo de divergência de *layout inteiro*. Custo: gráficos cujo tipo não tem equivalente interativo fiel (grids/anotações customizadas que a lib interativa não reproduz nativamente) ficam só estáticos, mesmo quando existe algum pacote que gera *algum* widget pro mesmo tipo — ter interatividade deixa de ser critério suficiente sozinho.
- **2026-07-27**: toda página de gráfico do site segue um **padrão fixo de conteúdo editorial** — ficha técnica no topo (pacotes, tipo de dado exigido, nível, tags) + 7 seções obrigatórias (o que é / quando usar e evitar / que dados precisa / como ler / como foi feito / possíveis problemas / variações) + o `script.R` renderizado com destaque de sintaxe e botão de copiar.
