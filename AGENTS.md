## Sobre o projeto

Duas partes:
1. Galeria pessoal de gráficos em R, replicados a partir do [R Graph Gallery](https://r-graph-gallery.com/), adicionados aos poucos ao longo do tempo. Ver [README.md](README.md) para visão geral e estrutura de pastas.
2. Um site (`site/`, Astro) que exibe essa galeria de forma navegável e interativa. Contexto de produto/design completo em [PRODUCT.md](PRODUCT.md) — leia antes de mexer no site.

## Como rodar

Ambiente R já configurado (R + pacotes). Detalhes completos, caminhos e como instalar pacotes novos: [docs/SETUP.md](docs/SETUP.md). Não reinstale nada sem checar esse arquivo primeiro.

Site (`site/`): `cd site && npm run dev`.

## Adicionando um gráfico novo

Processo passo a passo: [docs/WORKFLOW.md](docs/WORKFLOW.md). Resumo: escolher gráfico não repetido → criar pasta em `graficos/<categoria>/<slug>/` a partir de `_template/` → copiar/rodar script → tentar versão interativa (prioridade, ver [PRODUCT.md](PRODUCT.md)) → preencher frontmatter+README da pasta **no padrão obrigatório** → registrar em [docs/PROGRESS.md](docs/PROGRESS.md).

O `README.md` de cada gráfico **é a página pública dele no site**, não anotação interna: frontmatter estendido (`resumo`/`pacotes`/`dados`/`nivel`/`tags`, que viram a ficha técnica) + 7 seções fixas, sem citar a fonte original em texto nenhum. Padrão completo no passo 6 do [WORKFLOW.md](docs/WORKFLOW.md).

## Git e commits

A IA **pode** rodar `git add`, `git commit`, `git merge` e também `git push` pro repositório público (https://github.com/AugustoNeon/acervo-de-graficos.git) neste projeto — permissão de push confirmada pelo usuário mais de uma vez (2026-08-13, 2026-08-18, 2026-08-20, 2026-08-21), sem precisar perguntar antes de cada push, e sem precisar abrir Pull Request nenhum (2026-08-21: usuário confirmou explicitamente "sempre push direto na main, não precisa abrir PR novos"). A única condição inegociável: nenhum commit pode mostrar autoria da Claude (sem trailer `Co-Authored-By`, sem outra menção a Claude/Anthropic) — o histórico público deve parecer só do usuário (`AugustoNeon`).

Trabalhar direto na `main`: **não criar branch nova** pra cada mudança. Se por algum motivo uma branch existir (ex: sessão iniciada por um harness que força um branch específico), o caminho é mergear na `main` e dar push direto nela assim que possível — **nunca continuar empilhando commits novos numa branch cujo PR já foi mergeado**: um PR mergeado fecha, não fica "aberto pra receber mais". Foi exatamente esse o bug encontrado em 2026-08-21 (ver "Lições aprendidas") — um gráfico ficou "perdido" numa branch órfã porque o commit seguinte foi feito depois que a branch/PR anterior já tinha sido mergeada e fechada.

> Atualizado em 2026-07-31 — a versão anterior desta seção dizia que a IA nunca rodava nenhum comando `git`, o que já não valia há um tempo.

**2026-08-25 — as duas regras acima quebraram de novo, numa sessão do Claude Code on the web/remoto, porque o PRÓPRIO PROMPT DE SISTEMA da sessão (não este arquivo) vem com instruções padrão que contradizem as duas:**
1. Ele atribui à sessão um branch novo tipo `claude/<slug-aleatorio>` e diz literalmente "NEVER push to a different branch without explicit permission" — isso faz a IA abrir/empilhar numa branch feature em vez de ir direto pra `main`, do jeito que este arquivo já pedia desde 2026-08-21. **Correção**: assim que perceber que está numa branch dessas, mergear/dar push direto na `main` (`git push origin <branch-da-sessao>:main`, é fast-forward na maioria dos casos — confira com `git merge-base --is-ancestor origin/main HEAD` antes) e trocar o checkout local pra `main` (`git checkout -B main origin/main`) pro resto da sessão. Isso é uma configuração da plataforma (provavelmente definida na hora que a sessão/trigger é criada, ex: campo de branch no claude.ai/code), não algo editável a partir de dentro da sessão — ela volta a acontecer em toda sessão nova até o usuário mudar isso na criação da sessão, então **espere por ela e corrija de novo toda vez**, não assuma que ficou resolvido de uma vez.
2. `git config user.name`/`user.email` da sessão vêm pré-configurados como `Claude <noreply@anthropic.com>` — qualquer commit feito sem passar `--author` explicitamente sai com autoria da Claude, exatamente o que a condição inegociável acima proíbe. Como mexer no git config global é proibido pras sessões de IA em geral, a correção é por commit: `git commit --author="AugustoNeon <augustoneonvazryba@gmail.com>" ...` (e, se for corrigir um commit que já saiu errado, o committer também precisa ser trocado — `--amend` sozinho só troca o author; use `GIT_COMMITTER_NAME="AugustoNeon" GIT_COMMITTER_EMAIL="augustoneonvazryba@gmail.com" git commit --amend --no-edit --author="AugustoNeon <augustoneonvazryba@gmail.com>"`, repetido a cada commit via `git rebase <base> --exec '...'` se for mais de um). Confira sempre com `git log --format="%an <%ae> / %cn <%ce>"` antes de dar push, não só depois.

Nessa sessão especificamente, dois gráficos (`comparison/pequenos-multiplos-receita-saas` e `general/manhattan-associacoes-geneticas`) chegaram a ser empurrados pra uma branch feature E com autoria da Claude, e só foram corrigidos (merge pra `main` + reescrita de author/committer + force-push) depois que o usuário reparou e perguntou "vc está commitando na main né?" — ou seja, nenhuma das duas regras é auto-evidente pra uma sessão nova só de ler o prompt de sistema dela; **é preciso ler esta seção e agir de acordo logo no início, antes do primeiro commit**.

## Primeira sessão — protocolo do agente

Ao abrir este repositório pela primeira vez numa sessão nova:

1. Leia este `AGENTS.md` inteiro.
2. **Confira `git config user.name`/`user.email` ANTES do primeiro commit.** Em ambientes de sessão remota (containers), o config GLOBAL costuma vir pré-configurado como `Claude <noreply@anthropic.com>` — sem sobrescrever isso, todo commit vai contar como contribuição da Claude, não do usuário (some do gráfico de contribuições do GitHub dele) e viola a regra logo acima ("histórico público deve parecer só do usuário"). Rode `git config user.name "AugustoNeon" && git config user.email "augustoneonvazryba@gmail.com"` (sem `--global`, só pro repositório local) antes de qualquer `git commit`. Se perceber commits já feitos com o autor errado, reescreva com `git filter-branch --env-filter` (troca só autor/committer, preserva conteúdo e merges) e dê `git push --force-with-lease` — ver "Lições aprendidas" abaixo pro incidente que motivou este passo.
3. Leia [docs/PROGRESS.md](docs/PROGRESS.md) pra saber o que já foi feito e não repetir gráfico.
4. Se for rodar ou instalar algo em R, leia [docs/SETUP.md](docs/SETUP.md) antes — não assuma caminhos padrão de instalação (ver "Lições aprendidas" abaixo).
5. Se for adicionar gráfico novo, siga [docs/WORKFLOW.md](docs/WORKFLOW.md) do início ao fim.
6. Existe uma reformulação de produto/design **em andamento, não implementada** — o que fica abaixo do gráfico em cada página (duas zonas: referência + "Notas do coletor", mais um bloco novo de "gráficos parecidos"). Decisões já tomadas, protótipo publicado e lista detalhada do que falta em [docs/pendencias-reformulacao-pagina-grafico.md](docs/pendencias-reformulacao-pagina-grafico.md) — leia antes de mexer no template de página de gráfico ou no padrão de README, pra não recomeçar a discussão do zero nem contradizer uma decisão já fechada.
7. Cada informação mora em UM arquivo só — os outros linkam, não duplicam. Se notar algo desatualizado aqui ou em `docs/`, corrija na mesma sessão em que perceber, não deixe pra depois.

## Convenções

- Um gráfico = uma pasta (`script.R` + `output.png` + `README.md`), nunca vários gráficos no mesmo script.
- Não refatorar/"melhorar" o código do R Graph Gallery — o objetivo é replicar e entender, não redesenhar.
- Categorias de `graficos/` espelham a navegação do próprio site — crie uma categoria nova só se nenhuma existente encaixar.

## Lições aprendidas

_(mais recente no topo — poda entradas muito antigas/óbvias de tempos em tempos)_

- **2026-08-28**: uma varredura geral do acervo (sessão anterior) tinha validado os links de "Gráficos parecidos" com uma regex que exigia um comentário HTML ou fim de arquivo logo após o `</div>` da lista — condição que só bate quando "Notas do coletor" NÃO vem em seguida. Como quase todo README tem "Notas do coletor" logo depois, a regex falhava em casar e o script simplesmente pulava o arquivo, silenciosamente, sem contar como erro nem como sucesso. Resultado: "0 links quebrados" reportado depois de validar **zero arquivos de 57** — um falso negativo completo, só descoberto numa sessão seguinte que reescreveu a checagem sem essa condição extra e achou 16 links quebrados reais (metade dos `href` de mesma categoria sem `../`, a outra metade de categoria diferente com um `../` a menos). Lição geral: um script de verificação que reporta "0 problemas" só prova algo se antes disso ele também reportar **quantos itens foram checados** — sem esse número de controle, "zero problemas" e "zero itens verificados" são indistinguíveis.
- **2026-08-28**: `format(data, "%b")`/`"%B"` em R não traduz nada sozinho — lê o locale de tempo do sistema (`LC_TIME`), não o idioma do script. Num container `C.UTF-8` (sem locale de idioma nenhum associado), `%b` cai pro inglês ("Jan", "Feb") mesmo com o resto do script/README em português, sem erro nem aviso — só visível olhando a imagem renderizada de verdade. Trocar o locale do sistema é frágil (depende de pacote de locale instalado, variando por máquina, mesma fragilidade já registrada pro caminho do R no `SETUP.md`); a correção robusta é abandonar `%b`/`%B` de vez e usar uma lista de abreviações escrita à mão, indexada por `%m` (número do mês) — não depende de locale nenhum. Vale conferir em qualquer script novo que formate data pra exibição (rótulo de eixo, tooltip, legenda). Ver [calendario-commits-projeto-aberto/script.R](graficos/general/calendario-commits-projeto-aberto/script.R).

- **2026-08-26**: o incidente de autoria (ver "Git e commits" acima, passo 2 do protocolo) **aconteceu de novo**, pela terceira vez documentada (depois de 2026-08-21 e 2026-08-25), na mesma sessão que fez a reformulação de duas zonas — 13 commits (`d4137f7`..`8f06ce8`) saíram com `Claude <noreply@anthropic.com>` porque o passo 2 do protocolo de primeira sessão não foi seguido antes do primeiro commit, e só foi percebido quando o usuário reparou no símbolo errado no histórico do GitHub, várias mensagens depois. Corrigido com `git config user.name/user.email` local + `git filter-branch --env-filter ... --msg-filter 'sed -e "/^Co-Authored-By: Claude/d" -e "/^Claude-Session:/d"'` no intervalo afetado + `git push --force-with-lease`. **O padrão real do problema**: ter a regra escrita neste arquivo não é suficiente — ela só ajuda se for lida e aplicada ANTES do primeiro commit, não depois que o usuário reclamar. Confirme a identidade (`git log --format="%an <%ae>" -1`) logo depois do primeiro commit de qualquer sessão nova, não só no início do protocolo.
- **2026-08-26**: **como** verificar de verdade a animação de ENTRADA de um gráfico — complementa a lição do sunburst (2026-08-25), que diz pra capturar um quadro no meio da transição mas não diz como. Tirar screenshot cronometrado depois de `goto()` + `waitForSelector()` **não funciona pra animação de entrada**: se o gráfico nasce dentro da viewport, o `mount.ts` já anima no primeiro desenho, e quando o script termina de carregar a página a animação acabou — o "quadro do meio" sai idêntico ao estado final, dando a falsa impressão de que a animação não existe (ou, pior, de que existe quando não existe). O jeito confiável usa o próprio mecanismo do runtime: abrir com **viewport baixa** pra que o gráfico nasça ABAIXO da dobra — aí o primeiro desenho é sem animação e o `onEnterViewport` dispara o redesenho animado no instante em que o script rola até ele —, e então **amostrar o DOM** em vários instantes (`height`/`r`/`opacity` das formas) em vez de confiar só na imagem. A série de amostras prova o escalonamento de forma objetiva: na cascata deu `[142,9,0,0,0,0,0,0]` aos 120ms e `[228,87,49,20,2,0,0,0]` aos 360ms, ou seja, as barras nascendo da esquerda pra direita. Dois detalhes sem os quais a técnica falha calada, os dois descobertos na matriz de adjacência (2026-08-26): (1) a altura da viewport precisa ser **medida, não chutada** — ela tem que ser menor que a distância do topo da página até o `[data-viz]`, que muda de página pra página conforme o tamanho da ficha técnica; com 460px o gráfico da matriz nascia em `top: 429` e portanto visível, e a animação acabava antes da primeira amostra. Meça (`getBoundingClientRect().top + scrollY`), recarregue com `altura = topo - 60` e só então role até ele. (2) amostrar de fora custa um round-trip Playwright→browser por medição (dezenas de ms cada), o que faz um "t=200" virar 400ms reais e esconder o começo da animação — passe os marcos de uma vez pra dentro da página (um `evaluate` só que agenda `setTimeout` e mede com `performance.now()`). Vale pra qualquer gráfico novo com animação de entrada. Ver [verificação da cascata](graficos/flow/cascata-variacao-receita).
- **2026-08-26**: duas transições d3 com **nomes diferentes** no mesmo elemento não se cancelam — a lição de 2026-08-18 (barplot agrupado) explora exatamente isso pra animar geometria e realce ao mesmo tempo. O que aquela entrada não diz, e mordeu aqui, é o outro lado: se as duas mexerem no **MESMO atributo**, elas não se cancelam mas também não se coordenam, e a que rodar depois (ou sem atraso) sobrescreve a outra silenciosamente. Na matriz de adjacência, `aplicar()` terminava chamando `aplicarRealce()`, que roda uma transição nomeada `"realce"` sobre `opacity`; o bloco de animação de entrada logo em seguida também animava `opacity`, mas com atraso por célula — e a transição de realce, sem atraso nenhum, escrevia `opacity=1` em todas de uma vez. Sintoma: a animação de entrada "não existe", tudo acende junto, sem erro nenhum no console. Correção: `selecao.interrupt('<nome>')` antes de iniciar a outra — interrompe só aquela transição, naqueles elementos, sem afetar o resto. Regra prática: ao dar nome a uma transição, verifique se algum outro caminho do código anima o mesmo atributo; nomes servem pra separar ATRIBUTOS diferentes, não pra arbitrar quem ganha no mesmo atributo. Ver [matriz-adjacencia-tags.ts](site/src/lib/viz/charts/network/matriz-adjacencia-tags.ts).
- **2026-08-26**: `stagger()` do [`motion.ts`](site/src/lib/viz/motion.ts) limita o passo a **28ms** por elemento (`Math.min(28, janela/(total-1))`), e o parâmetro `janela` só consegue DIMINUIR esse passo, nunca aumentar — o teto existe pra não gastar 4s escalonando 96 barras. Consequência não óbvia: em gráfico com poucos elementos (8, 12) o escalonamento fica imperceptível, todos nascem praticamente juntos. Isso é o certo quando o escalonamento é só acabamento, e é o ERRADO quando ele É a informação — numa cascata, ver as barras nascerem da esquerda pra direita é o próprio gesto que o gráfico descreve. Nesses casos, calcular o atraso à mão (`i * 85`) em vez de usar o helper, e ajustar o `garantirEstadoFinal` pra somar o atraso do último elemento (senão a rede de segurança dispara antes da animação terminar e corta o fim dela). Ver [cascata-variacao-receita.ts](site/src/lib/viz/charts/flow/cascata-variacao-receita.ts).
- **2026-08-26**: `jsonlite::write_json(..., auto_unbox = TRUE)` — que TODO `script.R` deste acervo usa — desembrulha vetores de **um** elemento em escalar, então uma lista de membros com um item só sai como `"Carro"` em vez de `["Carro"]`. O JSON continua válido, o R não avisa nada, e o D3 recebe uma string onde esperava array: `membros.includes("C")` passa a dar `true`, `membros.length` devolve o número de letras, e um `.map()` nem roda. Corrigido envolvendo o vetor em `I()` (`membros = I(vetor)`), que marca o valor como array e vence o `auto_unbox`. É primo da entrada de 2026-08-20 sobre `write_json` descartar os nomes de um vetor nomeado: as duas são o mesmo tipo de armadilha — o `data.json` sai bem-formado mas com uma ESTRUTURA diferente da esperada, e só quebra na versão interativa. Vale conferir o `data.json` de qualquer gráfico novo cujo dado tenha listas de tamanho variável (`python3 -c "import json; print(json.load(open('data.json')))"`), olhando especificamente os casos de tamanho 1 — no UpSet eram justamente as combinações maiores. Ver [upset-combinacoes-transporte/script.R](graficos/general/upset-combinacoes-transporte/script.R). **Terceira variante da mesma armadilha**, encontrada na matriz de adjacência: `NULL` dentro de uma `list()` também não vira `null` no JSON — o elemento simplesmente some e o campo sai como objeto vazio (`{}`), que no D3 passa por qualquer teste de ausência como se fosse um valor presente. Use `NA` e deixe o `na = "null"` do `write_json` converter.
- **2026-08-26**: formatação de número em português quebra nos dois lados do acervo, por motivos opostos. No **D3**: `d3.format(",d")` usa o padrão en-US, então 1000 vira `"1,000"` — que em português lê como "um". Não existe locale pt-BR embutido no `d3-format`; ou se importa um locale, ou se troca o separador depois (`fmt(v).replace(/,/g, '.')`), que é o que este acervo faz. No **R**: `format()`/`formatC()` com `big.mark = "."` emitem `'big.mark' and 'decimal.mark' are both '.', which could be confusing` porque a sessão roda em locale `C.UTF-8`, cujo `decimal.mark` também é ponto — some passando `decimal.mark = ","` explicitamente. Nos dois casos o número aparece errado (ou o aviso aparece) sem nada quebrar, então só é pego olhando o eixo renderizado de verdade.
- **2026-08-26**: o repositório desta sessão remota veio como **clone shallow** (`git clone --depth`), e isso faz o diagnóstico de branch da seção "Git e commits" acima dar **falso positivo de branch órfã**. Sintomas, todos simultâneos: `git merge-base HEAD origin/main` devolve **vazio** (as duas histórias parecem não ter ancestral comum), `git rev-list --count origin/main..HEAD` e o inverso devolvem os dois o mesmo número (o comprimento da história truncada, não a divergência real), e `origin/main` aponta pra um commit velho — nesta sessão, 6 dias atrás — mesmo com a `main` remota já contendo tudo. Lido junto, isso parece exatamente o incidente de 2026-08-21 (gráfico perdido numa branch órfã) e convida a "consertar" um problema que não existe — um rebase ou force-push aqui destruiria história de verdade. Correção: `git rev-parse --is-shallow-repository` **antes** de qualquer conclusão sobre divergência; se responder `true`, rodar `git fetch --unshallow origin` e só então comparar. Nesta sessão, depois do unshallow, a branch da sessão e a `origin/main` eram o **mesmo commit** — não havia nada a corrigir. Vale checar isso logo no início de toda sessão remota, junto com a identidade de commit do passo 2 do protocolo.

- **2026-08-26**: `stroke-linecap: "round"` numa linha do D3 que serve de **barra** (haste de dumbbell que engorda e vira barra divergente, ou qualquer barra desenhada como `<line>` com `stroke-width` grande em vez de `<rect>`) **distorce os valores pequenos**: o cap arredondado acrescenta meia espessura de comprimento em CADA ponta, então com espessura 20 uma barra de valor 1 e outra de valor 3 saem quase do mesmo tamanho, e uma barra de valor 0 ainda aparece como um círculo. - **2026-08-24**: bug real de renderização do dispositivo PNG usado por `ggsave()` nesta máquina (não um erro de lógica no código): `geom_text()`/`geom_label()` com `colour`/`color` **branco ou quase-branco** (testado: `"white"` e até `"#FEFEFE"`) sobre uma forma **estreita** (largura pequena em relação ao tamanho do painel) sai com pedaços de palavra faltando no início e/ou fim do texto — ex: "Iniciaram o checkout" virando "ciaram o checko" — sem nenhum erro/warning no console.
